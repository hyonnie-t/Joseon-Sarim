# 사화 시뮬레이션 — 무오·기묘 (v1)

중3 역사 「[9역10-02] 사림 세력의 성장」 수업용 웹앱. history26 포털의 커리큘럼 활동으로 등록해서 쓴다.
설계 근거는 효니가 작성한 핸드오프 문서(`핸드오프_사화시뮬레이션_무오기묘_v1.md`)이며, 이 저장소는 그 문서의
콘텐츠·구조 요구사항을 구현한 것이다.

## 글쓰기①만 먼저 배포하기 (`write1/`)

전체 시뮬(15단계)과 별도로, `write1/index.html` 하나만 지금 바로 배포해서 쓸 수 있다. 로그인 확인 →
카드 분류(사림·훈구) → 카드 두 장 골라 한 마디 쓰기 → 복사해서 Padlet 붙여넣기 → 제출, 4단계만 있는
독립 페이지다(v1.2, 아래 changelog 참고 — 원래는 "비판할래/참을래 + 이유" 구조였다). GitHub Pages로
배포하면 `<Pages 주소>/write1/`로 접근한다.

- `../config.js`(`SHEET_WEBAPP_URL`, `PADLET_BY_BAN`)를 그대로 불러 쓴다 — 백엔드 URL이나 Padlet
  링크가 바뀌면 `config.js` 한 곳만 고치면 이 페이지에도 반영된다.
- `GAME_NAME`은 전체 시뮬과 다른 값(`write1/app.js`의 `WRITE1_GAME_NAME = '사화_글쓰기1_비판할래참을래'`)을
  쓴다 — 커리큘럼에 이 페이지를 별도 활동으로 등록할 때 이 값과 activity id를 맞출 것. 이름은 옛 구조
  때 지어진 것이지만, 이미 포털 커리큘럼에 이 값으로 등록돼 있을 수 있어 진행률·포인트 연결이 끊기지
  않도록 값 자체는 그대로 뒀다(내용만 바뀜).
- localStorage 키는 전체 시뮬과 똑같이 `joseon_sarim_progress_<학번>`을 쓴다. 다만 v1.2부터 그 안의
  필드가 `write1_classification`(카드별 분류 결과)/`write1_attempts`(확인 시도 횟수)/
  `write1_sarim_card`·`write1_hoongu_card`(고른 카드 id)/`write1_text`(한 마디)로 바뀌었다 — 옛
  `write1_choice`는 더 이상 쓰지 않는다. 전체 시뮬(`../app.js`/`../data.js`)의 `write1` 스텝과
  글쓰기②는 여전히 `write1_choice`/`write1_text`를 참조하므로, 같은 브라우저로 전체 시뮬을 먼저
  열어본 적 없는 학생이라도 이 글쓰기①만으로는 전체 시뮬 쪽 회고 화면이 "(기록 없음)"으로 뜬다 —
  핸드오프 문서 6장 "열린 질문 1"에서 효니 결정 대기 중인 사항이라 이번 범위(글쓰기① 화면만)에서는
  건드리지 않았다.
- 이 환경(개발 샌드박스)은 `script.google.com` 자체가 네트워크 정책으로 막혀 있어서 실제 제출까지는
  이 세션에서 못 찍어봤다. 코드 경로는 전체 시뮬의 검증된 제출 로직과 동일하게 맞췄지만, **효니가
  실제 배포 후 학번 하나로 실제 제출까지 한 번 확인해보는 걸 권장**한다.

## 포털 등록 방법

1. history26 교사 대시보드 "커리큘럼 관리" 탭에서 3학년 차시로 새 활동을 추가한다.
2. 활동 URL은 이 저장소를 GitHub Pages로 배포한 주소.
3. **activity id(=이 앱의 `CONFIG.GAME_NAME`)를 `config.js`의 값과 정확히 맞춘다.** 지금은
   `사화_무오기묘_시뮬레이션`으로 임시로 넣어뒀다 — 실제 차시 번호가 정해지면 `config.js`의
   `GAME_NAME` 값도 그 차시 id로 함께 바꿀 것 (예: `12차시_사화_판단시뮬` 같은 형태). 이 값이 안 맞으면
   포털 진행률·포인트 계산에 안 잡힌다.
4. 담당 학년/반: 3학년 5~8반. `config.js`의 `PADLET_BY_BAN`도 이 4개 반만 있다 — 다른 반이 열면
   회고 화면에 "담당 반 정보가 없어서 링크를 못 찾았어" 안내만 뜨고 앱 자체는 끝까지 진행된다.

## 화면 흐름

1. **학번·이름 확인** — 포털에서 `?sid=&name=`으로 넘어온 값을 화면에 띄우고 학생이 직접 확인/수정한다.
   자동 채움만 하고 화면을 건너뛰지 않는다(webapp-builder 스킬 필수 항목 — 값이 안 넘어왔거나 잘못
   넘어왔을 때 학생이 직접 고칠 수 있어야 한다). 5자리 학번 형식 + 이름 입력이 확인돼야 다음으로 넘어간다.
2. **글쓰기 ①** — 이제 이 앱 안에서 실제로 쓴다. 먼저 교과서 123쪽 서술 카드 10장을 사림/훈구로
   분류하고(전부 맞아야 다음으로 넘어가며, 틀리면 틀린 카드만 다시 보여준다), 그중 사림 카드 하나·
   훈구 카드 하나를 골라 훈구 대신들에게 한 마디(1~2문장)를 쓴다. 다 쓰면 "복사하기"로 클립보드에
   담고 Padlet 링크를 열어 붙여넣는 흐름(webapp-builder 스킬의 "마무리 글쓰기 후 패들렛 복사 기능").
   사화가 실제로 어떻게 벌어졌는지(결과)는 이 화면에 없다 — 결과를 모른 채 판단해야 하기 때문. 카드
   분류 자체가 사림·훈구 구도를 다루지만, 그건 교과서 123쪽이 이미 정리해 둔 구도이지 사화의 결과가
   아니다.
3. 무오사화 → 전환카드 → 기묘사화 → 전환카드 → 회고, 순서는 핸드오프 문서 6장 그대로.

## 데이터 저장 방식

- **localStorage**: 로그인 확인이 끝난 뒤 `joseon_sarim_progress_<학번>` 키로 진행 상황을 저장한다.
  새로고침해도 이어서 할 수 있고, 회고 화면 재표시에도 이 값을 그대로 쓴다.
- **Google Sheets(history26 백엔드)**: 회고 화면에 처음 도달하면(미리보기 모드 제외) 별도 action 없이
  기존 기본 제출 경로(POST body에 `gameName`만 있으면 게임활동_로그에 1행 기록되는 방식,
  `history26_backend/code.gs`의 `doPost` 기본 분기)로 한 번 제출한다. `choicesJson`에 전체 답변이
  JSON으로 들어가고, `reflection`에는 서술형 답변을 모아 사람이 읽기 좋은 형태로 넣는다. 실패하면
  `fetchJsonRetry`가 3회까지 재시도한다(간격 700ms, history26 관례와 동일). 재시도까지 실패하면
  회고 화면에 "기록 저장에 실패했어. 새로고침해서 다시 시도해봐" 문구만 뜬다(정오 판정이 아니므로
  담담한 문구 유지).
- `?preview=1`로 열면 시트 제출을 하지 않는다(교사 미리보기용). 로그인 확인 화면 자체는 미리보기여도
  그대로 뜬다 — 화면 흐름을 실제와 똑같이 보기 위함.

## 배포 후 수정 (v1.2, 2026-09-28) — 글쓰기① 구조 교체 (`write1/`만)

효니가 작성한 별도 핸드오프 문서("핸드오프 문서 v1 — 사림 단원 글쓰기 ① 수정")를 반영해
`write1/`(글쓰기① 독립 페이지)만 고쳤다. 전체 시뮬(`../app.js`/`../data.js`)·글쓰기②·`config.js`는
핸드오프 문서 7장 스코프 제한대로 건드리지 않았다.

- **바뀐 이유**: 옛 지시문 "훈구의 잘못이 눈에 보여"가 사림 쪽 시각을 사실처럼 전제했고, "123쪽에서
  근거 하나"는 "참는다"를 고른 학생에게 근거를 줄 수 없었다(123쪽 본문·각주에 참는 쪽 근거가 없음).
- **새 구조**: 1단계 카드 분류 → 2단계 카드 두 장(사림 1·훈구 1) 골라 한 마디(1~2문장) 쓰기. 카드
  10장 문구는 교과서 123쪽 서술 그대로(`write1/app.js`의 `CARDS` 배열, 임의 수정 금지).
- **열린 질문 처리 결과** (핸드오프 문서 6장):
  1. 글쓰기②/전체 시뮬과의 충돌 — 건드리지 않음(효니 결정 대기, 위 "글쓰기①만 먼저 배포하기" 절 참고).
  2. 최소 글자 수 — `write1/app.js`의 `MIN_TEXT_LEN = 10` 상수로 분리.
  3. 제출 후 예시 공개 — 넣지 않음(기본값 미노출 유지, 학생이 먼저 쓴 뒤 예시를 보여주는 기능 자체가 없음).
  4. 분류 인터랙션 — 드래그 없이 카드마다 [사림]/[훈구] 버튼만으로 구현했다. 두 방식을 병행하는
     안도 검토했지만, 네이티브 HTML5 드래그는 터치 기기에서 별도 처리가 필요해 태블릿 신뢰성이
     떨어지고, 이 분류는 카드 순서 재배열이 아니라 이분류(둘 중 하나 배정)라 버튼만으로도 완결성에
     문제가 없다고 판단했다 — "버튼만으로도 끝까지 진행 가능해야 한다"는 요건은 충족.
- **GAME_NAME 유지**: `WRITE1_GAME_NAME` 값(`사화_글쓰기1_비판할래참을래`)은 이름이 옛 구조를
  가리키지만, 이미 포털 커리큘럼에 이 activity id로 등록돼 있을 가능성이 있어 진행률·포인트 연결이
  끊기지 않도록 값은 바꾸지 않았다. 필요하면 커리큘럼 등록값과 함께 별도로 변경할 것.
- **데이터 수집**: 신규 액션/시트 없이 기존 기본 제출 경로 그대로. `choicesJson`에
  `{classification, attempts, sarim_card, hoongu_card, write1_text}`를 담고, `reflection`은
  기존처럼 서술형 텍스트(`write1_text`)만 넣는다.

## 배포 후 수정 (v1.1, 2026-09-28) — 장면 1 사료 카드 재설계

첫 배포본을 확인한 결과, 장면 1(무오사화)의 사료 카드가 중3이 읽기엔 과했다(핸드오프 문서 12장).
아래 두 가지를 고쳤다.

- **사료 카드 A(조의제문)**: 전문을 그대로 올렸던 걸, 판단에 실제로 쓰이는 세 문장만 발췌해서
  기본으로 보여주고(`data.js`의 `m_sourceA.source.text`), 전문은 `source.fullText`로 옮겨
  "🔎 궁금하면 전문 보기" 접이식 토글 뒤로 뺐다(`app.js` `renderSourceReveal()`). 원래 `source.easy`에만
  있고 렌더링되지 않던 학생용 쉬운 풀이 토글도 이번에 실제로 뜨도록 붙였다.
  질문은 자유서술 2개(q1: 의제가 어떻게 됐는지, q2: 쓴 이유 추론)였던 걸, 답이 원문에 그대로 있는
  q1은 선택형 4지선다로 바꾸고(정오 판정·피드백 없음, 그냥 선택만 저장) q2만 자유서술로 남겼다 —
  "화면당 자유서술형 1개" 원칙(핸드오프 12장에서 4장에 추가된 9번 항목) 적용.
- **사료 카드 B(왕의 해석)**: 대응관계 표를 6행에서 판단에 실제 쓰이는 2행(조룡=세조, 왕=노산)만
  남기고, "원문 그대로 보기" 토글과 조의제문 저작 의도 관련 2차 학설 디스클레이머는 학생 화면에서
  뺐다. 그 내용은 아래 "교사용 참고"로 옮겼다 — 데이터를 지운 게 아니라 화면에서만 뺀 것이다.
- 이미 평이한 교과서 문장(성종·훈구·사림 배경 설명)에 붙어 있던 학생용 쉬운 풀이 토글은 뺐다.
  이 토글은 사료 원문처럼 어려운 문장에만 쓰기로 원칙을 명확히 했다(K-2 말풍선·K-3 결과 인용에는
  그대로 유지 — 둘 다 실록 원문 고어체라 어려움).

### 교사용 참고 — 학생 화면에는 없음

사료 카드 B에서 뺀 두 가지. 필요하면 교사가 수업 중 구두로 보충하거나, 이후 별도 "더 알아보기" UI를
추가할 때 여기서 다시 가져다 쓴다.

- **전지문 원문 그대로** (K-1, 실록 확인): "그 '조룡(祖龍)이 아각(牙角)을 농(弄)했다.'는 조룡은
  진 시황(秦始皇)인데, 종직이 진 시황을 세조에게 비한 것이요, 그 '왕위를 얻되 백성의 소망을
  따랐다.'고 한 왕은 초 회왕(楚懷王)의 손자 심(心)인데, 처음에 항량(項梁)이 진(秦)을 치고 손심을
  찾아서 의제(義帝)를 삼았으니, 종직은 의제를 노산(魯山)에게 비한 것이다. 그 '양흔 낭탐(羊狠狼貪)하여
  관군(冠軍)을 함부로 무찔렀다.'고 한 것은, 종직이 양흔 낭탐으로 세조를 가리키고, 관군을 함부로
  무찌른 것으로 세조가 김종서(金宗瑞)를 베인 데 비한 것이요. 그 '어찌 잡아다가 제부(齊斧)에 기름칠
  아니 했느냐.'고 한 것은, 종직이 노산이 왜 세조를 잡아버리지 못했는가 하는 것이다. 그 '반서(反噬)를
  입어 해석(醢腊)이 되었다.'는 것은, 종직이 노산이 세조를 잡아버리지 못하고, 도리어 세조에게
  죽었느냐 하는 것이요. 그 '자양(紫陽)은 노필(老筆)을 따름이여, 생각이 진돈하여 흠흠하다.'고 한
  것은, 종직이 주자(朱子)를 자처하여 그 마음에 부(賦)를 짓는 것을, 《강목(綱目)》의 필(筆)에 비의한
  것이다."
- **조의제문 저작 의도 — 2차 학설, 원문 대조 전 [미확인]**: 조의제문을 쓴 의도가 실제로 무엇이었는지는
  학계 평가를 확인하지 못했다. 우리역사넷은 "세조의 왕위 찬탈을 비판한 것으로 평가되는" 글이라고
  쓴다(`S-GAPJA`). 학생 화면에서는 의도를 단정하지 않는다는 원칙을 지키되, 표 축소로 이 디스클레이머
  자체를 노출할 자리가 없어져서 뺐다 — 원칙이 바뀐 게 아니라 화면 구성이 바뀐 것.

## 완료 기준 검증

`node scripts/verify.mjs`로 핸드오프 문서 9장의 판정 가능한 기준(1~4번, 반복 실수 체크리스트)을
자동 검사한다. v1.1(장면 1 사료 카드 재설계) 반영 후 재실행 결과: **실패 0건** (사실 서술 노드 22개 —
sourceId 누락 0개, 힌트 7개 전부 물음표 종결, 정답/오답/점수/게이지 표현 0건, URL 원본 대조 전부 일치,
TDZ 방지 구조 확인).

`scripts/pw_test.py`는 Playwright로 768px 태블릿 폭에서 로그인 확인 화면부터 전체 15단계를 끝까지
진행하며 콘솔 에러를 수집한다(로컬 정적 서버 필요: `python3 -m http.server`). 로그인 확인 화면에
`?sid=&name=` 값이 실제로 노출되는지도 같이 검사한다. 사료 카드 A의 새 선택형 질문(`data-qkey`)도
자동으로 하나 골라서 진행하도록 맞췄다. v1.1 반영 후 재실행 결과: **JS 런타임 에러 0건**, 로그인
확인 화면에 학번/이름 정상 노출, 회고 화면에 글쓰기①·무오 판단·기묘 판단·해석 갈림 선택이 모두
정상적으로 재표시됨(기준 5, 6 충족).
콘솔에 뜨는 리소스 로딩 에러(Pretendard/Google Fonts CDN)는 이 개발 환경의 네트워크 정책 때문이며
실제 배포 환경(GitHub Pages, 일반 인터넷)에서는 발생하지 않는다.

카드 나열/순서 재배열 인터랙션은 이 앱에 없어서 반복 실수 체크리스트 3번(SortableJS+▲▼ 버튼)은
해당 없음이 정상이다.

## 파일 구조

- `index.html` — 뼈대(진행바, 스텝 영역, 이전/다음 버튼)만 담는다.
- `config.js` — 백엔드 URL, GAME_NAME, 반별 Padlet 링크.
- `data.js` — 모든 역사 서술·사료·문항. 새 사실 서술을 추가할 땐 반드시 `sourceId`/`verified`를
  같이 넣을 것(안 넣으면 `scripts/verify.mjs`가 잡아낸다).
- `app.js` — 렌더링/상태/제출 로직만. 역사 서술 문장을 여기 하드코딩하지 않는다.
- `style.css` — history26 포털과 같은 디자인 토큰(종이/먹/쪽빛/낙관) 재사용.
- `scripts/verify.mjs`, `scripts/pw_test.py` — 완료 기준 자동 검증용.
